# 候选标注判据 v1（2026-11-17，两条规则经用户批准）

v0 草案在 #12 上暴露过内部矛盾：kind 表把「已定稿的设计结论」列成 world 示例，
而排除条款说「代码/README 已体现的实现细节不提」——同一条候选用哪条判读会得出相反结论。
v1 的修法很简单：**先过排除条款，再定 kind**。

## 第 0 步：排除条款（先过这里，过了再看 kind）

一条候选**不该记**，只要命中任一条：

1. **三天测试不过**：三天后不再成立（"正在做""当下在做""刚刚聊到"、时点评价快照）；
2. **不影响未来行为**：代码 / README / 配置里已经写明的实现细节 —— 哪怕是定稿的设计结论；
3. **窗口结束时已不成立**：被后面的讨论推翻或修改过的要求（拿不准就标 `suspectStale` 交人核）；
4. 过程记录、一次性指令、纯代码或文件内容。

> 已批（用户，2026-11-17）：**README/代码已体现的实现细节一律不记，哪怕是定稿设计结论；
> 排除条款优先于 kind 表。** 依据：#12「详情就地展开」在 README 第 669 行已写明。

## 第 1 步：kind（排除条款过了才定）

| kind | 门槛 | 反例 |
|---|---|---|
| constraint | **硬性、长期、不许我做某事**的行为禁令（"不许/必须/别再"） | 设计要求、质量期望、UI 摆放 |
| world | 长期设定、结构、**已定稿的设计结论与否决** | 当下状态、过程描述、已写进文档的细节 |
| fact | 关于用户的稳定事实 / 偏好 / 特质 | 时点评价、一次性指令 |
| episode | 具体的共同经历（带场景、重要度） | 评价快照、迭代流水 |
| self | agent 自己的判断 / 失误 / 工作方式（第一人称） | 用户的经历 |

> 已批（用户，2026-11-17）：**设计否决 / 产物约束（"不要半透明"）归 world，不进 constraint。**
> constraint 的门槛是"不许 agent 做某事"，而这些约束的是**产物长什么样**。
> 把它塞进 constraint 的代价很具体：那个块每轮无条件付费，且会和后来的架构打架。

## 标注协议

- 两个标注者**各自独立标全部候选**（不是各标一半——没有重叠就算不出分歧率）；
- 分歧项与争议项**交用户裁决**，裁决结果才是"该记什么"的尺子；
- 模型互相同意不算金标（shuttle D2）。一致率高只说明两个模型共享同一套偏差。

## 输出格式

```json
{"n":1,"text":"…","verdict":"该记|不该记|争议","kindFix":null,"reason":"…","suspectStale":false}
```
