# 判据 v1.5：subject 映射（决定承载者）—— 先定判据，再逐条人标

四率（属性/主语/取值/极性）测不准的第一个原因是：**我把 subject 标成了"文本里提到了谁"，
而不是"这条决定约束的是谁"**。后者才跟 schema 的语义一致。判据先于标注，这一版就定这件事。

## 一句话判据

**看这条决定一旦被违反，谁必须改。**

| 违反后必须改的是 | subject | 例 |
|---|---|---|
| 我（助手）的行为或说法 | `agent` | 「先量再下结论」「直说但先给理由」「别在同一处反复调」 |
| 具体的产物（面板/插件/库/引擎/配置） | `product` | 「面板不要半透明」「帧率要有保证」「详情就地展开」 |
| 项目层面的方向或结构 | `project` | 「三款产品接入 dsh 做联动」「先做会成长的自我再接手脚」 |
| 谁都不用改，只是我得知道的事实或偏好 | `user` | 「用户不喜欢反复绕圈」「用户对流畅度敏感」「用户叫我这名字」 |
| 拿不准 / 主体不在上述四类 | `other` | 「旧识要记得用户」这类指向第三方的方向描述 |

## 四条消歧规则（按顺序判，先命中先用）

1. **先问"违反后谁改"**，再看句子里出现了谁。句子里出现"我"不等于 subject=agent。
2. **约束产物形态的一律 `product`**，即使句子开头是"用户要求面板…"——被约束的是面板，不是用户。
3. **约束我行为方式的 `agent`**，包括内核纪律、汇报口径、排障方式、说话风格。
4. **纯"我知道就好"的事实与偏好 `user`**；一旦它变成"某个产物必须怎样"，就归 `product`（规则 2 优先）。

## 与 schema 的关系

`subject` 是判等的第 2 条件（粗类相等，`other` 不参与并单报）。
所以标注时必须问的是**决定承载者**，不是"谁说的"。这一条定清楚，四率的主语一致率才有意义。

## 标注输出（逐条）

```json
{"n":1,"subjectGold":"product","attrGold":"风格","valueGold":"半透明","negativeGold":true,"reason":"违反后要改面板，所以是 product"}
```

两个标注者独立标同一批结构化输出，分歧交用户裁。

## 已知局限（先说，别假装解决）

粗类会把"面板"和"记忆库"都归到 `product`，**类内跨主语仍可能过配**
（「面板风格=深空」与「记忆库风格=深空」类内同 subject）。v1 接受这个代价换可比较性，
但报告里必须单列**类内跨主语误配率**，不假装闭集解决了全部跨主语问题。
