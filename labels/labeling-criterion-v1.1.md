## 第 0 步：排除条款（先过这里，过了再看 kind）

一条候选**不该记**，只要命中任一条：

1. **三天测试不过**：三天后不再成立（"正在做""当下在做""刚刚聊到"、时点评价快照）；
2. **是实现细节**：代码 / 配置里怎么写的、UI 摆放与交互细节 —— 哪怕 README 里写着；
3. **窗口结束时已不成立**：被后面的讨论推翻或修改过的要求（拿不准就标 `suspectStale` 交人核）；
4. 过程记录、一次性指令、纯代码或文件内容。

> 已批（用户，2026-11-17）：README/代码已体现的**实现细节**一律不记，排除条款优先于 kind 表。
> 注意这条排的是「细节」，不是「已被记载」——见下面的裁决。

## 已裁规则：库中已有等价物不能当"不该记"的理由

> 已批（用户，2026-11-18）：**「库里已有等价条目 / README 已写明」不能作为判"不该记"的依据。**
> 「该不该记」只问两件事：三天后是否仍成立、是否影响未来行为。
> 已经有等价条目，就标 `duplicateOf: <标签id>` 并**仍算"该记"**——去重是治理链的事，不是标注的事。

这条与规则②不冲突，因为排的东西不同：

- 规则② 排的是**实现细节**（"详情就地展开"这种交互规格，README 里怎么写就怎么跑）；
- 这条裁的是**"这条信息重要不重要"**不能拿"库里已经有了"来否 —— 否则标注者会拿库内容判候选不该记，
  转头又把同一批候选当召回标签，指标自己把自己抽空。

## 第 1 步：kind（排除条款过了才定）

| kind | 门槛 | 反例 |
|---|---|---|
| constraint | **硬性、长期、不许我做某事**的行为禁令（"不许/必须/别再"） | 设计要求、质量期望、UI 摆放 |
| world | 长期设定、结构、已定稿的设计结论与否决 | 当下状态、过程描述、实现细节 |
| fact | 关于用户的稳定事实 / 偏好 / 特质 | 时点评价、一次性指令 |
| episode | 具体的共同经历（带场景、重要度） | 评价快照、迭代流水 |
| self | agent 自己的判断 / 失误 / 工作方式（第一人称） | 用户的经历 |

> 已批（用户，2026-11-17）：设计否决 / 产物约束（"不要半透明"）归 world，不进 constraint。

## 标注协议

- 两个标注者**各自独立标全部候选**，分歧交用户裁，裁决结果才是尺子。
- 模型互相同意不算金标（shuttle D2）；一致率高只说明两个模型共享同一套偏差。
- 标注前先统一**文本键**（去空白、去引号、去尾标点），否则同一句会因为标点不同被当成两条。
